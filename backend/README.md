# LeadFlow API (backend)

FastAPI + SQLAlchemy 2 + Pydantic v2. Uses SQLite by default; any SQLAlchemy URL
(e.g. Postgres) works through `DATABASE_URL`.

## Run locally

Requires Python 3.11+.

```bash
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m app.seed                 # optional: load 7 demo leads
uvicorn app.main:app --reload --port 8000
```

- API: http://localhost:8000
- Interactive docs (Swagger): http://localhost:8000/docs

Tables are created automatically on startup. `python -m app.seed --reset` wipes the
data and re-seeds.

## Run with Docker

```bash
cd backend
docker build -t leadflow-api .
docker run -p 8000:8000 -e SEED_DEMO_DATA=true -v leadflow-data:/data leadflow-api
```

## Configuration

| Variable         | Default                   | Purpose                                          |
|------------------|---------------------------|--------------------------------------------------|
| `DATABASE_URL`   | `sqlite:///./leadflow.db` | SQLAlchemy database URL                          |
| `CORS_ORIGINS`   | `http://localhost:3000`   | Comma-separated origins allowed to call the API  |
| `SEED_DEMO_DATA` | `false`                   | Seed demo data on startup if there are no leads  |

See `.env.example`.

## Tests

```bash
cd backend
```

Each test runs against its own in-memory SQLite database.

## Data model

- **Lead**: `name` (required), `company`, `phone`, `status`, `follow_up_at`, timestamps.
- **Discussion**: belongs to a lead; `note`, optional `follow_up_at`, `created_at`, and
  `kind`:
  - `note`: written by the rep.
  - `system`: generated by the app ("Lead created.", "Status changed: New → Contacted").

Statuses: `new`, `contacted`, `qualified`, `proposal_sent`, `won`, `lost`.

All timestamps are stored in UTC and returned as ISO 8601 with a `Z` suffix. Inputs
that carry an offset are converted to UTC; inputs without one are treated as UTC.
Deciding what counts as "today" is left to the client, which knows the rep's
timezone.

## API

| Method | Path                              | Description                                         | Success | Errors   |
|--------|-----------------------------------|-----------------------------------------------------|---------|----------|
| GET    | `/api/leads?status=&search=`      | List leads with `last_note` / `last_discussion_at`  | 200     | 422      |
| POST   | `/api/leads`                      | Create a lead (status defaults to `new`)            | 201     | 422      |
| GET    | `/api/leads/{id}`                 | Get one lead                                        | 200     | 404      |
| PATCH  | `/api/leads/{id}`                 | Partial update (status, details, `follow_up_at`)    | 200     | 404, 422 |
| DELETE | `/api/leads/{id}`                 | Delete a lead and its discussions                   | 204     | 404      |
| GET    | `/api/leads/{id}/discussions`     | Timeline, newest first                              | 200     | 404      |
| POST   | `/api/leads/{id}/discussions`     | Log a note with an optional follow-up               | 201     | 404, 422 |
| GET    | `/health`                         | Liveness check                                      | 200     |          |

Behaviour worth knowing:

- **List order**: most recent activity first, i.e. the latest note, or the creation
  time for leads with no notes.
- **`last_note`**: only counts rep-written notes, not system entries.
- **`search`**: case-insensitive match on name or company.
- **Logging a discussion with `follow_up_at`**: the lead's `follow_up_at` is set to it
  in the same transaction. The response is `{ "discussion": ..., "lead": ... }`, so
  the client can update the list straight away.
- **Logging a discussion without a follow-up**: the lead's existing follow-up is kept.
- **Changing status**: adds a `system` entry to the timeline.
  `PATCH {"follow_up_at": null}` clears the follow-up.

Every error has the same shape: `{"detail": "Lead 42 not found"}`. Validation errors
(422) use FastAPI's standard list of field errors in `detail`. Unexpected errors are
logged server-side and returned as a generic 500.

### Examples

```bash
curl -X POST localhost:8000/api/leads -H 'content-type: application/json' \
  -d '{"name": "Sarah Connor", "company": "Acme Corp", "phone": "555-0199"}'

curl -X POST localhost:8000/api/leads/1/discussions -H 'content-type: application/json' \
  -d '{"note": "Sent pricing PDF", "follow_up_at": "2026-10-14T14:00:00+05:30"}'

curl -X PATCH localhost:8000/api/leads/1 -H 'content-type: application/json' \
  -d '{"status": "proposal_sent"}'
```
